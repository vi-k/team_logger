# Соглашения

Как здесь принято писать код, коммиты и документы. Правила рабочего цикла —
в `AGENTS.md`, устройство пакета — в `docs/architecture.md`.

## Код

Анализ строгий, и это не пожелание: `analysis_options.yaml` расширяет
`package:lints/recommended`, включает `strict-casts`, `strict-inference`,
`strict-raw-types` и большой ручной набор линтов. Из заметного:
`prefer_single_quotes`, `require_trailing_commas`, `prefer_const_constructors`,
`omit_local_variable_types`, `avoid_final_parameters`, `cascade_invocations`,
`sort_pub_dependencies`, `unreachable_from_main` (мёртвый код верхнего уровня
подсвечивается).

Перед тем как считать работу законченной:

```bash
dart format .
dart analyze     # должен быть чистым
dart test        # все тесты зелёные
```

Если правится пример — то же самое из `example/`.

**Все комментарии в `lib/`, `example/` и `test/` — по-английски, без
исключений.** Раньше `lib/src/loggable/` был исключением «исторически
по-русски»; 2026-08-23 переведены `lib/` (912 строк), `example/` (72) и
`test/` (183), и исключений больше нет. Всё это попадает в pub-архив и
видно на pub.dev, поэтому правило одно на все три каталога. Проверка:
`grep -rl '[А-Яа-яЁё]' lib/ example/ test/` не должен находить ничего. Без
`-P`: на macOS системный grep этого ключа не понимает, а диапазон в скобках
работает и там, и с GNU grep.

`tool/` в архив не идёт, и `tool/playground_data.dart` (13 строк) остаётся
по-русски — это внутренняя кухня, не артефакт пакета.

Русский остаётся только в документах для владельца и агентов — `AGENTS.md`,
`docs/`, `README.ru.md`.

Тесты обязательны для любого исправления поведения: сначала падающий тест,
фиксирующий дефект, потом починка. Тест — это и есть документация инварианта;
особенно это касается инвариантов санитайзера (см. `docs/architecture.md`).

## Публичный API и версии

Пакет живёт на ломающих изменениях, и имена в нём уже переезжали
(`activeLoggers`→`activeNamespaces`, `activeLevel`→`activeMinLevel`,
`collectionMaxLength`→`collectionMaxCount`, `LogStyle`↔`LogStyles`). Поэтому:

- любое изменение публичного API отражается в `CHANGELOG.md` — ломающие
  пункты помечаются `[breaking changes]`;
- версия в `pubspec.yaml` поднимается вместе с записью в `CHANGELOG.md`;
- состав публичного барреля стережёт `test/export_test.dart` — новый
  экспорт добавляется и туда;
- `.pubignore` держит внутреннюю кухню вне pub-архива (`AGENTS.md`,
  `CLAUDE.md`, `docs/`, `scripts/`, `screenshots/`).

## Коммиты

- По-английски, conventional-префикс: `feat:`, `fix:`, `docs:`, `test:`,
  `refactor:`, `chore:`. Ломающее изменение — `feat!:`/`fix!:`.
- Заголовок — повелительное наклонение, с маленькой буквы, без точки,
  умещается в ~72 символа.
- Тело объясняет **почему** и что именно ломалось, а не пересказывает дифф;
  переносы по ~72–76 символов.
- Мерж прямо в `main`, без PR.
- **Чужие правки не коммитить вместе со своими.** Если в рабочем дереве
  лежат изменения, которых ты не делал, добавляй в индекс только свои файлы
  и опиши чужие в `docs/handoff.md`.
- Единственное исключение из формата заголовка — релизный коммит:
  `Release X.Y.Z`, без префикса и с большой буквы. Он бывает только внутри
  связки публикации (см. ниже).

## Релиз

Пункты 1–6 агент делает сам, свободно: это обычные правки в дереве, любую
можно откатить. Пункт 7 — связка, которую запускает **только отдельный
запрос владельца**; правило целиком с обоснованием — в `AGENTS.md`,
раздел «Публикация на pub.dev».

1. Проверки зелёные в обоих пакетах: `dart analyze`, `dart test`,
   `dart format --output=none --set-exit-if-changed .` в корне и
   `dart analyze` в `example/`; `dart run example.dart` отрабатывает;
   `scripts/screenshots.sh --check` проходит (картинки README собраны
   из текущего кода).
2. Если менялись зависимости или их ограничения — пересобрана матрица
   Flutter: `flutter pub get` в пробном приложении с path-зависимостью,
   с `flutter_localizations` и без, на каждой поддерживаемой линии
   (почему именно так — `docs/architecture.md`).
3. `CHANGELOG.md` дополнен, ломающие пункты помечены
   `[breaking changes]`.
4. Версия поднята в `pubspec.yaml`.
5. `README.md` синхронизирован, если менялись публичные контракты, и
   вместе с ним `README.ru.md` (см. раздел выше); скриншоты перегенерированы
   `scripts/screenshots.sh`, если менялся вывод.
6. `dart pub publish --dry-run` — без предупреждений. Запускать можно
   всегда: он ничего не меняет ни в репозитории, ни на pub.dev.
7. **Связка, одним заходом и подряд:** коммит `Release X.Y.Z`, тег
   `vX.Y.Z`, push, `dart pub publish`. Ни одну часть по отдельности — ни
   коммит без тега, ни тег без публикации.
8. После публикации: запись об итогах волны в `docs/records/`, состояние —
   в `docs/handoff.md`.

Дойдя до пункта 7 без отдельного запроса, агент останавливается и говорит,
что ждёт его. Разрешения не спрашивать — вопросом его добывать нельзя.

## Документы

- Документы для владельца и агентов — по-русски: `AGENTS.md`, `docs/*.md`,
  `docs/records/`.
- Публичные артефакты — по-английски: `README.md`, `CHANGELOG.md`, dartdoc,
  сообщения коммитов, тексты ошибок.
- Переносы строк в markdown — по ~76 символов, как в `CHANGELOG.md`.
- В `README.md` не пишем о том, **как** готовилась документация: ни «измерено
  на симуляторе», ни «проверено прогоном», ни «а не выведено рассуждением».
  README — про библиотеку. Чем и как проверено утверждение, пишем в
  `docs/records/`.

### `README.ru.md`

Перевод `README.md` для владельца и агентов. Лежит в корне рядом с
оригиналом — так его видно.

**Из публикации его убирает единственная строка `README.ru.md` в
`.pubignore`.** В отличие от `docs/`, закрытого целиком, здесь защита
держится на одной строке: удалите её — и перевод уедет в архив и на pub.dev.
Не удалять и не переименовывать файл, не поправив `.pubignore`. Проверка —
`dart pub publish --dry-run`: в листинге не должно быть `README.ru`.

**Правило синхронности: правка `README.md` не считается законченной, пока не
обновлён перевод, и обе правки идут одним коммитом.** Перевод — не второй
источник истины: собственного содержания он не заводит, спорные места
решаются в пользу английского оригинала.

Чек-лист при правке README:

1. внести правку в `README.md`;
2. внести её же в `README.ru.md` — тот же раздел, то же место;
3. пути к картинкам в обоих файлах одинаковые (`screenshots/…`) — они
   лежат рядом;
4. код в примерах не переводится — переводятся только пояснительные
   комментарии; комментарии, показывающие вывод, остаются как есть;
5. сверить, что число разделов совпадает:
   `grep -c '^#\{2,4\} ' README.md README.ru.md`.

## Записи в `docs/records/`

Имя файла: `YYYY-MM-DD[N]-name-kind.md`. Квадратные скобки — литералы, `N` —
порядковый номер записи за день (`2026-07-30[3]-data-sanitizer-design.md`).

`kind` — одно слово о жанре записи, не о теме:

| kind | что это |
| --- | --- |
| `design` | устройство и API будущей работы (спека) |
| `plan` | план работ по спеке |
| `report` | отчёт о сделанном: волна правок, разбор дефекта, предмержевое ревью одной работы |
| `review` | полное ревью проекта: `project-review`, `architecture-review`, `flutter-review`, `bug-hunter`, `performance-review` — состояние всей кодовой базы глазами ревьюера, а не итог одной работы |

Нужного слова нет в списке — взять своё, по тому же принципу.

Каждый файл начинается с шапки текущего состояния:

```markdown
> **Состояние на YYYY-MM-DD:** что с этой работой сейчас — сделано и
> смержено (коммит), брошено, частично сделано, пересмотрено позже.
> **Что это:** одна фраза о содержимом.
> **Связанные записи:** имена других файлов в `docs/records/`.
```

Шапка живая: когда работа доделана, брошена или пересмотрена — шапка
обновляется, текст записи остаётся историей и не переписывается.

## Работа с ревью

В конец каждой находки дописывается вердикт по ней — отдельным абзацем, в
том же стиле, что и описание находки. Прозу самой находки при этом **не
трогать**: находка остаётся такой, какой её написал ревьюер, вердикт живёт
рядом.

Правило владельца: прежде чем задавать вопрос по находке или обсуждать её
решение, **сначала простыми словами описать саму находку** — что не так, как
воспроизводится, чем это грозит. Вопрос без такого описания владельцу
бесполезен: он вынужден реконструировать контекст сам.
