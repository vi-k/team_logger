# FileLogStorage — сессионное сохранение логов в файлы

Дата: 2026-07-27
Статус: на ревью

## Цель

Дать приложениям возможность сохранять логи на устройстве пользователя для
последующей отправки на диагностику. Логи хранятся посессионно: каждый запуск
приложения — отдельная сессия со своими файлами. Количество сессий не
ограничивается; ограничиваются размер сессии, суммарный размер всех сессий
и время жизни старых сессий.

## Решения, принятые при обсуждении

- **Формат** — JSON Lines: одна строка = один лог в JSON.
- **`data`** — пользователь выбирает формат: `objectToString` (по умолчанию)
  или `objectToJson`. Для `objectToString` задаётся тема
  (по умолчанию `LogMainTheme.noColors`). ANSI-коды **сохраняются** в файле.
- **Три лимита размера** (количество чанков и сессий не ограничивается):
  `maxTotalSize` — все сессии вместе (старейшие сессии удаляются целиком),
  `maxSessionSize` — одна сессия (ротация чанков: при превышении удаляется
  самый старый чанк, свежие логи сохраняются всегда),
  `maxChunkSize` — один чанк (по достижении лимита чанк закрывается и
  открывается следующий). Явный лимит чанка выбран вместо производного
  `maxSize ~/ chunks`: после введения ротации на новый чанк при ошибках
  записи количество чанков не фиксировано, и параметр «число чанков»
  вводил бы в заблуждение.
- **Метаданные** — первой строкой файла: sessionId, время старта и
  произвольные поля приложения (версия, устройство и т.п.).
- **Web** — не поддерживается: функциональность живёт в отдельном экспорте
  `team_logger_io.dart` (dart:io); основной `team_logger.dart` остаётся
  кросс-платформенным.
- **Экспорт** — сессии в один файл **не** склеиваются: каждая сессия
  экспортируется отдельным файлом (чанки сессии собираются в один файл).
  Сжатие — отдельным методом `archiveTo`: один ZIP-архив на несколько
  сессий, внутри архива каждая сессия — отдельный файл. Сама отправка
  (HTTP, почта и т.п.) — зона ответственности приложения.

## Архитектура

Пайплайн пакета не меняется: **Logger → Log → Publisher**. Добавляется новый
publisher — `FileLogStorage`, построенный на `AsyncPublisherWithBufferBase<Log>`
из `logger_builder`: логи копятся в буфере и пишутся на диск батчами в фоне,
вызов логирования ничего не блокирует. `flush()` (из `HasFlush`) гарантирует,
что всё опубликованное записано на диск.

### Файлы

```
lib/team_logger_io.dart                      # новый экспорт: team_logger + file storage
lib/src/file_storage/file_log_storage.dart   # publisher
lib/src/file_storage/file_log_codec.dart     # Log -> строка JSON, meta-строка
lib/src/file_storage/file_log_sessions.dart  # листинг/чтение/экспорт/удаление сессий
```

`team_logger_io.dart` реэкспортирует `team_logger.dart` целиком, чтобы на
не-web платформах хватало одного импорта.

## Публичный API

### FileLogStorage

```dart
final class FileLogStorage extends AsyncPublisherWithBufferBase<Log> {
  FileLogStorage({
    required String directory,        // папка для логов, создаётся рекурсивно
    String? sessionId,                // по умолчанию — из времени старта (UTC)
    Map<String, Object?>? meta,       // пользовательские поля meta-строки
    int minLevel = LogLevels.all,
    int maxSessionSize = 10 * 1024 * 1024, // лимит одной сессии, байт
    int maxChunkSize = 1024 * 1024,        // лимит одного чанка, байт
    int? maxTotalSize,                // лимит всех сессий вместе; null — без лимита
    Duration? maxAge = const Duration(days: 7), // TTL старых сессий; null — вечно
    FileLogDataFormat dataFormat = FileLogDataFormat.text,
    LogMainTheme? theme,              // по умолчанию LogMainTheme.noColors
    LoggableConfig config = const LoggableConfig(),        // для text-режима
    LoggableJsonConfig jsonConfig = const LoggableJsonConfig(), // для json-режима
    void Function(Object error, StackTrace stackTrace)? onError,
  });

  String get directory;
  String get sessionId;
  FileLogSessions get sessions;      // reader, привязанный к directory

  // унаследовано: publish(log), flush(), close()
}

enum FileLogDataFormat { text, json }
```

### FileLogSessions / FileLogSession

```dart
final class FileLogSessions {
  FileLogSessions(String directory);

  /// Все сессии в папке, отсортированы от старой к новой.
  Future<List<FileLogSession>> list();

  /// Экспортирует каждую из указанных сессий (по умолчанию все) отдельным
  /// файлом `<sessionId>.jsonl` в папку target. Чанки сессии собираются
  /// в один файл, meta-строка — ровно одна, первой строкой. Существующие
  /// файлы перезаписываются. Возвращает созданные файлы.
  Future<List<File>> exportTo(
    Directory target, {
    Iterable<FileLogSession>? sessions,
  });

  /// Собирает указанные сессии (по умолчанию все) в один ZIP-архив target.
  /// Внутри архива каждая сессия — отдельный файл `<sessionId>.jsonl`
  /// (тот же формат, что у exportTo). Существующий target перезаписывается.
  Future<void> archiveTo(
    File target, {
    Iterable<FileLogSession>? sessions,
  });
}

final class FileLogSession {
  String get id;
  List<File> get files;        // чанки в порядке возрастания индекса
  int get size;                // суммарный размер, байт (на момент list())
  DateTime get lastModified;   // последняя активность (на момент list())

  Future<Map<String, Object?>> readMeta(); // содержимое meta-строки
  Stream<List<int>> read();          // конкатенация чанков (meta-строки чанков
                                     // после первого пропускаются)
  Future<String> readAsString();
  Future<void> delete();
}
```

Текущая сессия попадает в `list()` наравне с остальными — приложение отличает
её сравнением `session.id == storage.sessionId`. Перед экспортом текущей
сессии приложение вызывает `await storage.flush()`.

## Формат хранения

### Имена файлов

```
<sessionId>.<index>.jsonl        # например 20260727-143059-482913.1.jsonl
```

- `sessionId` по умолчанию — время старта UTC в виде `yyyyMMdd-HHmmss-микросекунды`
  (лексикографически сортируется по времени). Пользовательский `sessionId`
  санитизируется: символы, недопустимые в именах файлов, и точки заменяются
  на `_`. При коллизии с существующей сессией добавляется числовой суффикс
  (`-1`, `-2`, …).
- `index` — номер чанка, начиная с `1`, монотонно растёт и не переиспользуется
  после удаления старых чанков (у долгой сессии остаются, например, чанки 17–24).
- Файлы, не подходящие под маску `*.N.jsonl`, игнорируются листингом и очисткой.

### Meta-строка

Первой строкой **каждого** чанка (чтобы ротация её не теряла) пишется:

```json
{":meta":{"sessionId":"20260727-143059-482913","started":"2026-07-27T09:30:59.482913Z","appVersion":"1.2.3"}}
```

- `sessionId` и `started` (UTC ISO-8601) добавляются пакетом всегда;
  поля из параметра `meta` подмешиваются на тот же уровень (зарезервированные
  ключи `sessionId`/`started` пакет перезаписывает).
- Ключ `":meta"` следует конвенции служебных ключей пакета (`:v`, `:u`)
  и не может быть спутан со строкой лога.
- При экспорте и в `read()` meta-строки чанков после первого пропускаются —
  в собранном файле сессии метаданные ровно одной, первой строкой.

### Строка лога

Один JSON-объект на строку (`\n` в конце). Пустые/отсутствующие поля
опускаются:

```json
{"num":42,"level":300,"levelName":"info","time":"2026-07-27T09:30:59.482913Z",
 "path":"app/network","traceIds":["req:a1b2"],"message":"GET /users",
 "tags":["http"],"data":"{url: 'https://…', status: 200}",
 "error":"SocketException: …","stackTrace":"#0 …"}
```

- `time` — ISO-8601 в UTC.
- `message` — всегда прогоняется через тему уровня
  (`theme[log.level]`): `formatMessage(formatValue(...))` — BBCode
  компилируется, ANSI-коды из темы сохраняются как есть. С дефолтной
  `noColors` ANSI-кодов нет, а BBCode-теги остаются в тексте литерально
  (как и в консольном выводе этой темы); тема `noColorsNoTags` убирает
  теги без ANSI.
- `data` (только если `log.hasData`):
  - `FileLogDataFormat.text` — строка из
    `Loggable.objectToString(log.data, theme: theme[log.level], config: config)`,
    ANSI сохраняется;
  - `FileLogDataFormat.json` — объект из
    `Loggable.objectToJson(log.data, config: jsonConfig)`.
- `traceIds` — список `toString()` каждого `TraceId`.
- `error`/`stackTrace` — `toString()`.

## Ротация чанков

Три независимых лимита размера: `maxTotalSize` ≥ `maxSessionSize` ≥
`2 * maxChunkSize`. Количество чанков и сессий не ограничивается.

- Батч дописывается в текущий чанк. Если после записи размер чанка
  `>= maxChunkSize`, чанк закрывается и открывается следующий (`index + 1`).
- После закрытия чанка старые чанки удаляются, пока суммарный размер
  сессии превышает `maxSessionSize` (текущий чанк не удаляется никогда).
- Батч режется по `maxChunkSize`: большой батч (например, накопившийся за
  время инициализации) распределяется по нескольким чанкам, а не пишется
  одним куском.
- Строка лога никогда не разрезается между чанками; строка длиннее
  `maxChunkSize` пишется целиком (чанк может разово превысить лимит).
- Инвариант `maxSessionSize >= 2 * maxChunkSize` (assert) гарантирует, что
  в сессии живут минимум два чанка и ротация не выбрасывает всю историю
  разом.
- Итог: на диске хранится «хвост» сессии размером примерно
  `maxSessionSize − maxChunkSize … maxSessionSize`.

## Очистка при старте: TTL и суммарный лимит

При создании `FileLogStorage` (асинхронная инициализация) папка сканируется
и выполняются две очистки; текущая сессия не трогается никогда:

1. **TTL** — сессии, у которых `lastModified` самого нового чанка старше
   `now − maxAge`, удаляются целиком. `maxAge = null` отключает очистку.
2. **Суммарный лимит** — если задан `maxTotalSize`, старейшие сессии
   (по `lastModified`) удаляются целиком, пока суммарный размер остальных
   сессий превышает `maxTotalSize − maxSessionSize` (резерв под рост текущей
   сессии до её лимита).

Очистка выполняется только на старте — фонового таймера нет: рост во время
работы даёт только текущая сессия, а она ограничена `maxSessionSize`. Активная
сессия другого изолята/процесса защищена тем, что постоянно обновляет
`lastModified` (документируется: `maxAge` должен быть заметно больше
интервалов записи).

## Экспорт и сжатие

- `exportTo(target, ...)` пишет в папку `target` по одному несжатому файлу
  `<sessionId>.jsonl` на сессию: чанки в порядке возрастания индекса,
  meta-строка ровно одна (первая), далее строки логов в хронологическом
  порядке.
- `archiveTo(target, ...)` — отдельный метод для сжатия: собирает выбранные
  сессии в **один** ZIP-архив (`package:archive`, pure Dart). Внутри архива
  каждая сессия — отдельный файл `<sessionId>.jsonl` с тем же содержимым,
  что дал бы `exportTo`. Один вызов — один файл для отправки на диагностику.
- Сессии в один JSONL-файл не объединяются никогда — ни на диске,
  ни в архиве.
- Экспортированные файлы не соответствуют маске чанков `*.N.jsonl`, поэтому
  даже при экспорте в папку логов они не попадут в листинг и под очистку.
- Новая зависимость пакета: `archive` (ZIP-кодек, pure Dart).

## Жизненный цикл и ошибки

- Конструктор синхронный; внутри стартует `Future` инициализации
  (создание папки → очистки → выбор `sessionId` без коллизий →
  **резервирование сессии**: первый чанк создаётся эксклюзивно
  (`create(exclusive: true)`) сразу с meta-строкой — два инстанса с
  одинаковым id не могут затереть друг друга; при занятом файле id получает
  следующий суффикс). Все записи — только append, файлы никогда не
  усекаются. При создании каждого чанка первой строкой пишется meta-строка.
  Логи, опубликованные до завершения инициализации, копятся в буфере
  базового класса.
- `handle(batch)` ждёт инициализацию, кодирует строки и дописывает в чанки
  с `flush: true` — после `await storage.flush()` всё гарантированно
  на диске.
- Изоляция ошибок:
  - meta кодируется через `Loggable.objectToJson` и никогда не бросает:
    невалидные значения деградируют до строкового представления, в худшем
    случае meta-строка содержит только `sessionId`/`started`;
  - ошибка кодирования одного лога (бросающий `toString()` и т.п.) не
    теряет соседние логи батча — вместо лога пишется fallback-строка
    с полем `encodeError`;
  - ошибка ввода-вывода при записи: батч **не** возвращается в retryBuffer
    (иначе мёртвый диск даст бесконечный цикл и рост памяти) — вызывается
    `onError`, батч отбрасывается, а запись **переходит на новый чанк**
    (частично записанная строка не склеится со следующей в невалидный
    JSONL);
  - исключение из пользовательского `onError` проглатывается (иначе оно
    подвешивало бы `flush()` unhandled-ошибкой в зоне);
  - ошибка инициализации: `onError`, storage переходит в состояние
    «отключён» (публикации молча игнорируются, ошибка не повторяется).
- `publish` после `close()` — молчаливый no-op (базовый класс бросал бы
  `StateError` в точку логирования и подвешивал `flush()`).
- `close()` дописывает буфер и закрывает storage.
- `assert(maxTotalSize >= maxSessionSize)` — отрицательный резерв молча
  удалял бы все старые сессии; `assert(maxSessionSize >= 2 * maxChunkSize)` —
  иначе ротация не сохраняла бы хвост.

## Тестирование

Все тесты — на реальной файловой системе во временных папках
(`Directory.systemTemp.createTemp`), время — через `package:clock`
(`withClock`) для TTL-тестов.

1. **Кодек**: полная схема строки; опускание пустых полей; `data` в обоих
   режимах; сохранение ANSI при цветной теме; компиляция BBCode в message;
   `time` в UTC; meta-строка (авто-поля + пользовательские, перезапись
   зарезервированных ключей).
2. **Ротация**: маленькие `maxSessionSize`/`maxChunkSize` → правильные
   имена и число чанков, удаление старейших, сохранение хвоста, строка
   больше `maxChunkSize`,
   meta-строка в каждом чанке.
3. **Очистка**: TTL удаляет старые сессии, свежие и текущую — нет;
   `maxAge: null` не удаляет ничего; `maxTotalSize` удаляет старейшие сессии
   с учётом резерва; чужие файлы в папке не трогаются.
4. **Сессии**: `list()` (порядок, size, lastModified), `readMeta()`,
   `read()`/`readAsString()` (дедупликация meta-строк), `delete()`.
5. **Экспорт**: файл на каждую сессию; порядок строк; одна meta-строка;
   перезапись существующих файлов; `archiveTo` — ZIP-раундтрип (распаковка
   даёт по файлу на сессию с тем же содержимым, что `exportTo`), выбор
   подмножества сессий.
6. **Жизненный цикл**: `flush()` — всё на диске; публикация до завершения
   инициализации не теряется; `onError` при недоступной папке.

## Отклонённые альтернативы

- **Синхронная запись в `publish()`** — блокирует event loop на I/O;
  в `logger_builder` уже есть готовая асинхронная база с буфером.
- **Абстракция хранилища (для web и т.п.)** — отклонена при обсуждении:
  лишняя поверхность API; web-пользователи просто не подключают
  `team_logger_io.dart`.
- **Один файл с усечением** — при достижении лимита пришлось бы либо терять
  свежие логи, либо переписывать файл целиком; цепочка чанков дешевле и
  сохраняет хвост.
- **Склейка всех сессий в один файл при экспорте** — отклонена при
  обсуждении: каждая сессия — отдельный файл.

## Вне скоупа

- Отправка логов (HTTP/Sentry/почта) — на стороне приложения.
- Сжатие чанков на диске (хранение сжатым) — сжимается только экспорт.
