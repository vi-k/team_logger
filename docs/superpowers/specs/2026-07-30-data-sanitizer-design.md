# Санитайзация значений data до публикации

Дата: 2026-07-30
Статус: на ревью

## Цель

Дать возможность обработать **каждое значение** внутри `data` до публикации
лога: маскировать секреты и PII во вложенных структурах, вырезать поля
целиком. Дополняет `Logger.transformer` (team_logger 0.5.2), который умеет
заменить `data` только целиком.

## Решения, принятые при обсуждении

- **Точка санитайза — создание лога**, а не форматирование: рекурсивный
  обход строит НОВУЮ структуру, и `Log.data` хранит только очищенное.
  Fail-closed: все publisher'ы, in-memory [LogStorage] и любой кастомный
  код видят только очищенные значения. Цена — обход дублирует type-switch
  форматтера и материализует структуру заранее (см. «Издержки»).
- **Подключение — через готовые хуки 0.5.2**, без новых точек в ядре:
  `logger.transformer = sanitizeData(...)` глобально (наследуется
  сублоггерами) или `TransformPublisher(fileStorage, transformer:
  sanitizeData(...))` для одного назначения.
- **Правило — колбэк с контекстом**: получает имя, значение, полный путь
  (`user.card.number`) и глубину. Путь ленивый: собирается только при
  обращении к `ctx.path`, иначе правило по `ctx.name` не платит
  аллокациями.
- **Обходятся все узлы**, включая контейнеры. Возврат значения, отличного
  от исходного, останавливает обход внутрь (можно вырезать поддерево одним
  правилом). Отдельный маркер `Sanitize.drop` убирает поле из вывода
  целиком — не «***», а отсутствие ключа.

## Публичный API

```dart
typedef LogValueSanitizer = Object? Function(SanitizeContext ctx);

final class SanitizeContext {
  /// Имя свойства или ключ Map; `null` для элементов коллекций и корня.
  final String? name;

  /// Значение, которое реально попадёт в вывод (см. «Правило view»).
  final Object? value;

  /// Глубина: 0 — корневой объект `data`.
  final int depth;

  /// Путь от корня: `user.card.number`, `items[0].pan`. Собирается
  /// лениво.
  String get path;
}

/// Маркеры санитайзера.
final class Sanitize {
  /// Вернуть из санитайзера, чтобы поле исчезло из вывода целиком.
  static const Object drop = ...;
}
```

Обход как самостоятельная утилита (симметрично `Loggable.objectToString`
и `objectToJson`):

```dart
static Object? Loggable.sanitize(
  Object? obj,
  LogValueSanitizer sanitizer, {
  String cycleMarker = '<cycle>',
  int maxIterableCount = 1000,
});
```

Склейка с логом:

```dart
LogTransformer<Log> sanitizeData(
  LogValueSanitizer sanitizer, {
  String cycleMarker = '<cycle>',
  int maxIterableCount = 1000,
});
```

Использование:

```dart
log.transformer = sanitizeData(
  (ctx) => switch (ctx.name) {
    'password' || 'token' => Sanitize.drop,
    'creditCard' => '<redacted>',      // внутрь объекта обход не идёт
    _ => ctx.path.endsWith('user.email') ? maskEmail(ctx.value) : ctx.value,
  },
);
```

## Семантика обхода

| Узел | Что видит санитайзер | `Sanitize.drop` |
| --- | --- | --- |
| корень `data` | `name: null`, `depth: 0`, `path: ''` | `data` → `Log.noData` |
| свойство `Prop` | `name` = имя свойства | свойство удаляется |
| запись `Map` | `name` = `key.toString()` | запись удаляется |
| элемент `List`/`Set`/`Iterable` | `name: null`, путь `…[i]` | элемент удаляется |

Возврат значения, **идентичного** исходному (`identical`), означает «не
трогал» — обход продолжается внутрь контейнера. Любое другое значение
подставляется как есть, внутрь него обход не идёт (в том числе если это
новый контейнер: пользователь отвечает за то, что положил).

Ключи `Map` не санитайзятся: они видны санитайзеру как `ctx.name`, и
удалить запись по ключу можно через `Sanitize.drop`.

## Правило view (закрытие утечки)

`Prop` несёт и `value`, и `view`, а рендерится `view`, если он задан
(`Prop.toLogString`/`toMapEntry`). Санитайзация одного `value` оставила бы
секрет в `view`.

- Санитайзер получает **то, что реально рендерится**:
  `view` (если он не `Prop.noView`), иначе `value`. Для `computed`-свойств
  это как раз `view` — иначе санитайзер видел бы служебную заглушку.
- При **любой** замене свойство пересобирается как
  `Prop(name, sanitizedValue, view: Prop.noView, …)` — от оригинала не
  остаётся ни `value`, ни `view`. Остальные атрибуты (`showName`,
  `hidden`, `config`) сохраняются.
- Если санитайзер вернул значение без изменений, свойство остаётся
  нетронутым целиком: у свойства с `view` исходный `value` сохраняется в
  структуре, но он и не рендерится (побеждает `view`, который санитайзер
  и видел).
- `LoggableView` в `view` подпадает под то же правило: заменяется целиком.

## Обрабатываемые типы

Обход повторяет type-switch форматтера, иначе непокрытый тип стал бы
дырой:

- примитивы (`null`, `bool`, `num`, `String`, `Enum`, `DateTime`,
  `Duration`) — листья;
- `Map` → новый `Map` с очищенными значениями (порядок сохраняется);
- `List`/`Set` → новые `List`/`Set`;
- прочие `Iterable` → материализуются в `List` (см. «Издержки»);
- зарегистрированный `LoggableTypeConverter` → `convertToData(obj)` и
  санитайз полученного `LoggableData` (иначе поля стороннего типа
  прошли бы мимо санитайзера);
- `Loggable` → `logClassInfo()` → санитайз `LoggableData`;
- `LoggableData` (включая приватные builder-подклассы) → новый экземпляр
  того же подкласса с очищенными `props` — через новый package-private
  `copyWithProps`, чтобы рендеринг не изменился;
- `LoggableWrapper` → санитайз внутреннего `data`, `config` сохраняется;
- `LoggableMultiData` → санитайз значений, ключи и `config` сохраняются;
- любой другой объект — лист (рендерится через `toString()`).

## Циклы

Обход защищён стеком «посещаемых» объектов по `identical` (как в
форматтере). Обратная ссылка на предка заменяется строкой `cycleMarker`
(по умолчанию `'<cycle>'`).

Оставить в этом месте оригинальный объект нельзя: это была бы **утечка** —
у форматтера сработала бы своя защита от циклов только при совпадении
идентичности, а копия и оригинал — разные объекты, и сырое поддерево
отрисовалось бы целиком. Нотация `↺ₙ` для санитайзнутых данных теряется:
она вычисляется на этапе форматирования, до которого сырой структуры уже
нет.

## Ошибки

Санитайзер, бросивший исключение, не обрабатывается отдельно: исключение
выходит из `sanitizeData`-трансформера, и дальше работает механика 0.5.2 —
лог **не публикуется**, ошибка уходит в `onError`
(`TransformPublisher`) или в `Zone.current.handleUncaughtError`
(`logger.transformer`). Fail-closed без нового кода.

## Издержки (документируются)

- `collectLoggableData` у `Loggable`-объектов вызывается на этапе
  логирования, а не форматирования: логи, отфильтрованные publisher'ом
  позже, всё равно оплачивают сбор свойств.
- Ленивые `Iterable` материализуются. Сегодня их спасают лимиты
  форматтера, поэтому бесконечный `Iterable` завис бы. Ограничение —
  `maxIterableCount` (по умолчанию 1000): лишнее отбрасывается, в конец
  добавляется маркер усечения `'…'`.
- Структура копируется целиком; для больших `data` это лишние аллокации на
  горячем пути логирования.

## Что вне рамок

- `message`, `error`, `stackTrace`, теги и путь — их правит обычный
  `Log.copyWith` внутри того же трансформера.
- Санитайзация ключей `Map` (см. выше).
- Готовые правила-редакторы (`Redact.mask`, `Redact.last4`): осознанно не
  делаем — примитив + композиция, как в остальном пакете.

## Тестирование

- Обход: примитивы; `Map`/`List`/`Set`/`Iterable`; вложенность; `name`,
  `depth`, `path` (включая индексы `[i]`); ленивость `path`.
- `Sanitize.drop` в каждой позиции таблицы (корень, свойство, запись Map,
  элемент коллекции).
- Замена контейнера останавливает обход внутрь.
- Правило view: свойство с `view`, `computed`, `fixed`/`round`,
  `LoggableView` — после замены ни `value`, ни `view` не содержат
  оригинала.
- `Loggable`-объект, `LoggableData`-builder'ы (рендеринг совпадает с
  несанитайзнутым при тождественном санитайзере), `LoggableWrapper`,
  `LoggableMultiData`, зарегистрированный конвертер.
- Циклы: самоссылка и взаимная ссылка → `cycleMarker`, без зависания.
- `maxIterableCount`: бесконечный `Iterable` не вешает логирование.
- e2e: секрет не доходит ни до `ConsoleLogPrinter`, ни до JSONL
  `FileLogStorage`; бросающий санитайзер = лог не опубликован (fail-closed).
