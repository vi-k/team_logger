> **Состояние на 2026-08-21:** исправлено в `b20f797`; реализация прошла
> RED–GREEN, полный набор проверок, сфокусированный performance-probe,
> независимое ревью и clean publish dry-run.
> **Что это:** исправление находки №7 полного ревью без поэлементного
> копирования в горячем пути.
> **Связанная запись:** `2026-08-21[1]-project-review.md`.

## Проблема и контракт

`Log` документирован как immutable record, но раньше сохранял публичные
`tags` и `traceIds` по ссылке. Владелец исходной коллекции либо первый
publisher мог изменить уже принятое событие до того, как его увидит следующий
publisher или асинхронное хранилище.

Новый контракт: обе коллекции — unmodifiable snapshots. Публичный конструктор
и новые значения в `copyWith` делают одну defensive copy. `copyWith` без
замены сохраняет identity готовых snapshots, чтобы transformer не копировал
их на каждом логе.

Обычный `Logger` находится на более узкой границе владения: он сам создаёт
свежие list/set и после конструктора их больше не использует. Внутренний
`Log._owned` закрывает эти коллекции unmodifiable view без копирования
элементов. Для самого частого случая без tags/traceIds используются
константные пустые коллекции.

## TDD

До production-изменения три теста дали ожидаемый RED:

- изменение исходных коллекций меняло `Log` после публичного конструктора;
- изменение replacements меняло результат `copyWith`;
- `log.tags.add()` успешно менял опубликованную запись.

Characterization отдельно подтвердила существующий performance-инвариант:
`copyWith` без replacement уже передавал обе коллекции по identity. После
минимальной реализации весь файл — 11/11, ближайшие logger/transformer/storage
потребители — 36/36.

Независимое ревью нашло промежуточную регрессию порядка lazy evaluation:
call tags разрешались раньше path/message и снимка logger tags. Отдельный тест
дал RED `tags → message` вместо прежнего `message → tags`; set-spread перенесён
после path/message, порядок и snapshot-семантика восстановлены.

## Производительность

Один и тот же локальный JIT-probe запускал девять измерений каждого сценария
до и после изменения; ниже медианы:

| Сценарий | До | После | Изменение |
| --- | ---: | ---: | ---: |
| plain log | 128 нс/op | 119 нс/op | −7% |
| tags + traceId | 214 нс/op | 218 нс/op | +2% |
| transformer с `copyWith` | 162 нс/op | 157 нс/op | −3% |

Probe не является стабильным межмашинным benchmark. У context-path baseline
samples были 210–228 нс/op, финальные — 216–220 нс/op: диапазоны перекрываются,
поэтому +1,9% медианы не доказывает регрессию. Plain-path больше не создаёт
временный пустой trace list, но сохраняет временный tag set для исходного
порядка lazy evaluation; в самом `Log` обе пустые коллекции канонические.
Context-path не копирует элементы, но добавляет две маленькие view-обёртки,
необходимые для запрета мутации.
