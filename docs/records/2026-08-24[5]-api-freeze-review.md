# Ревизия публичной поверхности перед заморозкой

Состояние на 2026-08-24. Последний пункт плана `2026-08-24[2]-road-to-1.0.md`.
Единственный вопрос к каждому имени: **о чём мы пожалеем, если оставим это
навсегда.**

Политики, на которых стоит ревизия, — `docs/conventions.md`, раздел
«Заморозка API на 1.0». Главное из них: **консольный рендер не
замораживается**, поэтому вопросы вида «а если поменяется вид вывода» здесь
не возникают вовсе.

## Замеры

| Что | Значение |

## Находки

### 1. `GrowableConstraintsValues` — мёртвый публичный класс

**Не используется нигде.** Во всём репозитории — два упоминания, и оба
собственные: объявление `lib/src/printer/constraints.dart:115` и его
конструктор. Ни `lib/`, ни `test/`, ни `example/`, ни README.

Изменяемый класс с публичным полем `List<LogConstraints> values`, без
дартдока. Заморозить его — значит обещать навсегда то, чего не зовёт даже
сам пакет.

**Предложение: удалить.** Ломающее, поэтому только до 1.0.

### 2. `AnsiStringExtensions` кладёт метод на каждую `String`

`extensions.dart` в бочке, а в нём `extension AnsiStringExtensions on String`
с методом `applyConstraints(Log, LogTheme, LogConstraints, …)`.

Проверено в стороннем пакете: `'hello'.applyConstraints` резолвится. То есть
**любой, кто импортирует `team_logger`, получает лишний метод на все свои
строки**, и метод этот — машинерия принтера, требующая `Log` и `LogTheme`.

Цена не только в шуме. Если приложение или другой пакет объявит своё
`applyConstraints` на `String`, Dart сообщит об **неоднозначности расширения**
на месте вызова, и разбираться пользователю придётся с нашим именем.

Внутри пакета зовётся только из `lib/src/printer/log_block.dart`. Снаружи —
ниоткуда: ни тесты, ни пример.

**Предложение: убрать из бочки** (расширение остаётся, перестаёт быть
публичным).

### 3. `MeasuredLineExtensions` — расширение типа, которого нет наружу

`extension MeasuredLineExtensions on MeasuredLine`, при этом
`measured_line.dart` **в бочку не входит**. Пользователь видит расширение в
справочнике, но не может назвать тип, к которому оно применяется, — то есть
воспользоваться им нельзя в принципе.

Зовётся оттуда же, что и находка 2, и только оттуда.

**Предложение: убрать из бочки вместе с находкой 2.**

### 4. Сентинелы `LogNoData` и `LoggableNoView` — публичны и не описаны

Оба — `final class` с приватным конструктором (`LogNoData._()`,
`LoggableNoView._()`), без дартдока, существуют ради единственного значения:
`Log.noData` и `Prop.noView`. Сконструировать нельзя, а проверять `is
LogNoData` незачем — для этого есть `Log.hasData`.

Убрать их дороже, чем кажется: типы стоят в сигнатурах `Log.noData` и
`Prop.noView`, и, чтобы имена исчезли из справочника, эти члены пришлось бы
типизировать как `Object`.

**Предложение: оставить, но написать дартдок** — раз имя замораживается, оно
обязано объяснять, что это и почему его нельзя создать.

### 5. `LogThemeData` — 173 члена в одном типе

Не находка, а мера обязательства: это самый крупный тип пакета и заметная
доля всей поверхности. Замораживая его, замораживаем 173 члена поимённо.

Ревизии по существу здесь не проводилось — она сама по себе работа. Если
владелец хочет пройти по нему отдельно, это делается **до** 1.0; если нет,
решение «замораживаем как есть» должно быть осознанным, а не случайным.

## Не находки — проверено и снято

- **29 имён не упомянуты в README** — само по себе не дефект. Большая часть
  из них — типы, которые пользователь получает из других имён и обязан
  уметь назвать: `FileLogSession` и `FileLogSessions` (`storage.sessions`),
  `LogStorageEvent` с наследниками (`LogStorage.onChanged`), `LevelLogger`
  (`logger[level]`), `LogTheme` (`LogMainTheme.info`), типдефы `LogFn`,
  `LogNumberFormatter`, `LogThemeFormatter`, `LogValueSanitizer`. Убирать
  нечего; следствие в том, что для этой части API справочник — единственная
  документация.
- **Модификаторы классов** расставлены осмысленно: `final` там, где не
  наследуют, `abstract interface` там, где реализуют. Отдельного решения не
  требуют.
- **`@Deprecated` в `lib/` нет**, то есть в 1.0 не уезжает ни одного мостика
  (в `logger_builder` такой был — `HasFlush`, убран в 0.8.0).

## Работа, если находки приняты

1. Удалить `GrowableConstraintsValues`.
2. Убрать `src/printer/extensions.dart` из `lib/team_logger.dart`.
3. Дартдок для `LogNoData` и `LoggableNoView`.
4. Решить по `LogThemeData`: ревизовать отдельно или замораживать как есть.

Пункты 1 и 2 ломающие — только до 1.0. Пункт 3 — нет, но делать его после
заморозки поздно по смыслу: имя уже будет обещано.
