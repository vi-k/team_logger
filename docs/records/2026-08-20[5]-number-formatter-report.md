# Форматирование чисел уехало в тему

Сделано ровно по спеке и плану, отклонений от них нет. Ниже — что вышло и
что при этом выяснилось.

## Что теперь есть

```dart
typedef LogNumberFormatter = String Function(
  LogTheme theme,
  num value,
  String pattern,
);

// LogMainTheme
final LogNumberFormatter numberFormatter;   // default: value.toString()

// LogTheme
String formatNumber(num value, String pattern) =>
    main.numberFormatter(this, value, pattern);
```

Рендереры `Loggable._intToString`/`_doubleToString` зовут
`theme.formatNumber(obj, f)` вместо `format('{:$f}', obj)`. Импорт
`package:format` из `lib/` ушёл целиком: осталась одна ссылка на пакет — в
dartdoc, ссылкой на pub.dev.

`format` переехал в `dev_dependencies`. У потребителя он из графа исчез —
проверено на пробном Flutter-приложении: в lock'е 3.27 +
`flutter_localizations` записи `format` больше нет.

## Строка в конфиге — целый шаблон

Это второе решение владельца и главная ломающая часть.
`LoggableConfig.intFormat`/`doubleFormat` не поменяли ни имени, ни типа,
но содержимое другое: `'{:,d}'` вместо `',d'`, `'{:.4f}'` вместо `'.4f'`.
Пакет строку не разбирает и не достраивает — передаёт как есть.

Побочный эффект, ради которого это и делалось: подключить можно не только
брейсы. `(theme, value, pattern) => sprintf(pattern, [value])` — и в
конфиге пишут `'%d'`. Или свою функцию, не имеющую отношения к `format`.

## Дефолт — тихий `toString()`

Тема без форматтера шаблон игнорирует. Владелец сначала выбрал «бросать»,
но при разборе выяснилось, что `Loggable.objectToString` и `toString()`
рендерят через `const LogTheme.noColors`, в которую форматтер положить
нечем, — то есть интерполяция `'$obj'` роняла бы вызывающий код без
всякой возможности это исправить на месте. Решение сменили на тихое, и
оно закрыло вопрос целиком: nullable-параметров `theme:`, статических
запасок и настраиваемого `Loggable.defaultTheme` не понадобилось.

Цена названа в CHANGELOG прямо: у того, кто обновится и не прочтёт его,
`intFormat: ',d'` молча начнёт печатать `123456789`. Взамен пропала
противоположная неприятность — невалидный спецификатор больше не роняет
логирование сам по себе, бросить может только форматтер, который поставил
сам пользователь.

## Мелочи, которые стоит знать

- **Вывод `example.dart` — 376 строк вместо 374.** Не из-за чисел:
  пример печатает саму тему (`log.d('$LogMainTheme', data: theme)`), а у
  темы прибавилось поле.
- **`screenshots/data_6.png` не переснимался.** Numbers-блок при верном
  рецепте рендерится байт-в-байт как раньше: `1.2346`, `123,456,789`,
  `0x75bcd15`.
- **`numberFormatter` печатается в `collectLoggableData` без сэмпла**, в
  отличие от соседних `countFormatter`/`indexFormatter`, которые
  показывают себя на примере. Любой пример шаблона был бы синтаксисом
  конкретного форматтера — ровно то знание, которое отсюда вынесли.
- **dartdoc нового поля — по-английски**, хотя у соседей по файлу
  (`cycleFormatter`, `ansiCodesEnabled`) он по-русски. Правило
  `docs/conventions.md` требует английского для dartdoc, исключение из
  `AGENTS.md` про русские комментарии касается `lib/src/loggable/`, а
  шапка класса `LogMainTheme` и так по-английски.
- **`comment_references: true`** в `analysis_options.yaml` не даёт
  сослаться из `log_main_theme.dart` на `LoggableConfig.intFormat`
  квадратными скобками: этот файл его не импортирует, а импорт был бы
  циклом (`loggable_config.dart` сам импортирует тему). В dartdoc там
  обратные кавычки.
