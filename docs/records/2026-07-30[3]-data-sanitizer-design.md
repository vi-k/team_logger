# Санитайзация значений data при выводе

Дата: 2026-07-30
Статус: на ревью (v2 — после пересмотра точки санитайза)

## Цель

Дать возможность обработать **каждое значение** внутри `data`: маскировать
секреты и PII во вложенных структурах, вырезать поля целиком. Дополняет
`Logger.transformer` (0.5.2), который умеет заменить `data` только
целиком.

## История решения

Первая редакция спеки санитайзила `data` **при создании лога**: обход
строил новую структуру, и `Log.data` хранил только очищенное. От этого
отказались: цена оказалась выше пользы.

- Ломалась ключевая гарантия пакета «отфильтрованные логи ничего не
  стоят»: `collectLoggableData` вызывался бы на каждый лог, даже если
  publisher его потом отбрасывает.
- Требовался параллельный type-switch, который надо держать в синхроне с
  форматтером.
- Требовалась собственная защита от циклов (с потерей нотации `↺ₙ`) и
  материализация ленивых `Iterable` с искусственным лимитом — прямая
  регрессия: сегодня бесконечный `Iterable` выводится нормально.

Итог: санитайзим **в момент вывода**, в существующих обходчиках
`objectToString`/`objectToJson`. Всё перечисленное выше исчезает —
лень, циклы и лимиты коллекций работают как раньше.

**Цена, которую принимаем осознанно:** сырое значение остаётся в
`Log.data`. Отрисовано оно не будет нигде (см. «Полнота покрытия»), но
живёт в памяти — в кольцевом буфере `LogStorage`, в heap-дампе, и утечёт,
если кастомный publisher возьмёт `log.data` в обход loggable-API
(`jsonEncode(log.data)`).

Контракт колбэка при этом такой же, как был бы у обхода-пересборщика,
поэтому дверь не закрыта: если гарантия «в памяти чисто» понадобится,
режим «санитайз при создании» добавляется сверху с теми же правилами.

## Решения, принятые при обсуждении

- **Точка санитайза — вывод**, а не создание лога.
- **Санитайзер глобальный**: одна регистрация на приложение
  (`Loggable.sanitizer`), как уже сделано у `registerTypeConverter`.
  Забыть его на конкретном publisher'е невозможно; применяется и в
  in-app просмотрщике логов, и при экспорте сессий. Разные правила для
  консоли и файла так не сделать — это осознанный размен.
- **Правило — колбэк с контекстом**: имя, значение, полный путь
  (`user.card.number`), глубина. Путь ленивый: собирается только при
  обращении к `ctx.path`.
- **Обходятся все узлы**, включая контейнеры: возврат значения,
  отличного от исходного, подставляется вместо него, и внутрь
  **оригинала** обход не идёт. Маркер `Sanitize.drop` убирает поле из
  вывода целиком.

## Публичный API

```dart
typedef LogValueSanitizer = Object? Function(SanitizeContext ctx);

final class SanitizeContext {
  /// Имя свойства, ключ Map или записи multi-data; `null` для элементов
  /// коллекций и для корневого значения.
  final String? name;

  /// Значение, которое реально попадёт в вывод (для свойства с `view` —
  /// сам объект `view`, а не его текст, см. «Правило view»).
  final Object? value;

  /// Глубина: 0 — корневое значение.
  final int depth;

  /// Путь от корня: `user.card.number`, `items[0].pan`. Собирается
  /// лениво; контекст действителен только во время вызова.
  String get path;
}

abstract final class Sanitize {
  /// Убирает значение из вывода целиком.
  static const Object drop = ...;
}

// в Loggable:
/// Глобальный санитайзер; `null` (по умолчанию) — вывод без обработки.
static LogValueSanitizer? sanitizer;
```

Использование:

```dart
Loggable.sanitizer = (ctx) => switch (ctx.name) {
  'password' || 'token' => Sanitize.drop,
  'creditCard' => '<redacted>',       // внутрь оригинала обход не идёт
  _ => ctx.path.endsWith('user.email') ? maskEmail(ctx.value) : ctx.value,
};
```

### Замена рендерится как обычное значение

Обход не идёт внутрь **оригинала**: его дети правилу не предлагаются
вовсе. Но подставленное значение рендерится обычным путём — через
`objectToString`/`objectToJson`, — поэтому **его собственные дети
предлагаются правилу** наравне с любыми другими значениями.

Это осознанный выбор: замена, которую подсунуло правило, — такие же
данные, и оставлять их неотсанитайзенными было бы менее безопасно.
Плата — правило, возвращающее контейнер, внутри которого лежит значение,
снова подходящее под то же правило, зациклится:

```dart
// Так нельзя: замена содержит 'secret', правило сработает на неё снова.
Loggable.sanitizer = (ctx) =>
    ctx.value == 'secret' ? {'was': 'secret'} : ctx.value;
```

### Правило не должно рендерить и логировать

Из того же следует ограничение на само правило: внутри него нельзя звать
`objectToString`/`objectToJson`, интерполировать `'${ctx.value}'` для
`Loggable`/`LoggableData`/`LoggableWrapper`/`LoggableMultiData` (их
`toString` заходит в те же обходчики) и нельзя логировать. Корневая
позиция защищена сегментом-заглушкой, поэтому нарушение контракта не
вешает процесс, но приводит к лишним проходам по структуре.

### Изоляты

`Loggable.sanitizer` — статическое поле, то есть живёт в пределах одного
изолята. Правило, установленное в главном изоляте, не применится к
логам, отрисованным в порождённом: там его надо установить заново.

## Где именно применяется санитайзер

Значение санитайзится **ровно один раз** — тем местом, которое знает его
позицию:

| Место | `ctx.name` | сегмент пути | `Sanitize.drop` |
| --- | --- | --- | --- |
| `Prop` (свойство `LoggableData`) | имя свойства | `.name` | свойство не рендерится |
| запись `Map` | ключ, как его рисует этот вывод (см. ниже) | `.key` | запись не рендерится |
| элемент `List`/`Set`/`Iterable` | `null` | `[i]` | замена на `'<dropped>'` |
| запись `LoggableMultiData` | ключ | `.key` | запись не рендерится |
| корневое значение | `null` | — | пустой вывод |

Строковый ключ `Map` даёт одно и то же имя в обоих выводах. Нестроковый —
разное: имя должно совпадать с НАПЕЧАТАННЫМ ключом (оно же — сегмент
пути, и считается один раз, тем же рендером, что идёт в вывод), а рисуют
ключ два вывода по-разному. Строковый — обходчиком и темой
(`[₌₂ ₀:1, ₁:2]`, `.admin`), JSON — через `key.toString()` (`[1, 2]`,
`Role.admin`). Сводить эти формы к одной нельзя: тогда имя перестало бы
описывать вывод. Практическое следствие — правило по тексту нестрокового
ключа сработает в одном выводе и пропустит запись в другом; такие записи
редактируются по значению либо выбрасываются целиком.

`objectToString`/`objectToJson` применяют санитайзер **только к корню** —
когда стек пути пуст. Для вложенных значений он уже применён родителем,
повторно не вызывается.

Корень предлагают и прямые пользовательские пути, в обходчики не
заходящие: `Loggable.toString`, `LoggableData.toString`,
`LoggableMultiData.toString` и `LogMessage` в принтере. Класс,
подмешавший `Loggable`, тем самым принял, что его `toString` — это
рендеринг лога, и свойства там санитайзятся; оставлять непредложенным
один только корень было бы рассогласованием. Практическое следствие:
правило по `depth == 0` влияет и на `'$obj'`/`print(obj)`, а
`Sanitize.drop` в корне даёт на этом пути пустую строку.

Чтобы корень не был предложен дважды, обходчик держит сегмент-заглушку в
стеке **на весь рендер корня**, а не только вокруг замены: иначе
`toString()` любого `Loggable`, до которого рендер доберётся напрямую
(ключ `Map`, интерполяция внутри чужого `toString`), увидел бы пустой
стек и сделал бы свой корневой офер.

«Отброшено» сообщается вне полосы — отдельным полем `dropped`, а не
пустой строкой: замена вправе легитимно отрендериться в пустоту
(`Loggable.builder` без свойств), и по тексту дроп от неё не отличить.
По той же причине обход секций multi-data сообщает вызывающему, были ли
записи отброшены: multi-data со ВСЕМИ выброшенными секциями блок данных
не печатает, а пустая сама по себе — двоеточие сохраняет.

Стек сегментов — статический, рядом с существующим `_visiting`, поэтому
сигнатуры `objectToString`/`objectToJson` не меняются.

Ключи `Map` не санитайзятся: они видны как `ctx.name`, и убрать запись
можно через `Sanitize.drop`.

**Почему `drop` не удаляет элемент коллекции.** Коллекции печатают свою
длину (`[₌₅ ₀:first, …]`) и режут вывод по бюджету `maxLength`. Удаление
элемента рассогласовало бы счётчик с содержимым и сломало бы бюджет,
причём по-разному в двух путях вывода (с лимитами и без). Поэтому в этой
позиции `drop` трактуется как замена на `'<dropped>'`: длина остаётся
честной, значение не выводится. Для «поле должно исчезнуть» есть
именованные позиции.

## Правило view (закрытие утечки)

`Prop` несёт и `value`, и `view`, а рендерится `view`, если он задан.
Критично: **ни одна реализация `LoggableView` не проходит через
`objectToString`/`objectToJson`** — `_LoggableView`,
`_LoggableViewConvert` и `LoggableMultiView` формируют строку и JSON
напрямую (`'$value'`, `.toString()`, `converter(...)`). Поэтому хук,
живущий только в обходчиках, `view` не увидел бы вовсе.

- Санитайзер получает **то, что реально рендерится**: `view`, если он не
  `Prop.noView`, иначе `value`. Для `computed`-свойств это как раз
  `view` — иначе санитайзер видел бы служебную заглушку.
- **Слепое пятно, которое из этого следует.** `ctx.value` для такого
  свойства — сам объект `view`, а не текст, который он нарисует.
  Правило, смотрящее на содержимое, `view` не разглядит:
  `prop('card', pan, view: LoggableView.convert<String>((v, _, __) =>
  'PAN=$v'))` предложит правилу `_LoggableViewConvert<String>`, а
  напечатает `PAN=4111…`; условие вида «в значении есть 4111» не
  сработает. То же верно для сырого не-`num` view, внутри которого лежит
  структура. Позиция при этом предлагается **ровно один раз**, поэтому
  правила по `name` и `path` работают: свойства с `view` редактируются
  по имени или пути, а не по содержимому. Это задокументировано в
  дартдоке `SanitizeContext.value`.
- Если санитайзер вернул замену, она рендерится напрямую как обычное
  значение через `objectToString`/`objectToJson`: логика `view` (включая
  `units` и `LoggableView`) не применяется — иначе замена прошла бы через
  форматирование, рассчитанное на оригинал. То же правило действует и в
  корне: замена наследует конфигурацию контейнера (`collectionMaxCount`,
  `stringInQuotes`, форматы чисел — это про способ печати), но НЕ его
  `units` — единицы утверждают что-то об исходной величине, а маска ею
  не является.
- Если вернул значение без изменений — рендеринг ровно как сегодня.

### Почему не пропустить сам `view` через обходчики

Рассматривали вариант «пусть `Prop` и реализации `LoggableView` рендерят
через `objectToString`/`objectToJson`» — тогда хук в обходчиках увидел бы
`view` сам, без отдельной врезки. Отклонено:

- **Меняется вывод.** Сегодня `view` печатается интерполяцией, поэтому
  строковые view идут без кавычек: `lat: 27.99` (view от `fixed`),
  `total: computed-str`. Через `objectToString` те же значения дают
  `lat: "27.99"` и `total: "computed-str"` — кавычки появляются везде, где
  используются `fixed`/`round`/`computed`/сырой view, включая скриншоты
  README.
- **Ломается формат JSONL.** Сейчас view помечается маркером:
  `{"lat": {":view": "27.99"}}` — потребитель отличает отображение от
  сырого значения. Через `objectToJson` останется `{"lat": "27.99"}`.
- **Двойное форматирование.** `_LoggableViewConvert` зовёт
  пользовательский конвертер, который обычно уже вернул готовую строку;
  прогонять её через форматтер второй раз незачем.
- **Покрытия это не добавляет.** Хук ставится на объект `view` в `Prop`
  ДО того, как включается любая машинерия `LoggableView`, поэтому все
  реализации — включая будущие — покрыты автоматически. Роутинг через
  обходчики добавил бы риск без выигрыша в безопасности.

Унификация рендеринга view через обходчики может быть осмысленной сама по
себе (например, чтобы view-коллекция печаталась по правилам пакета, а не
через `toString()`), но это отдельное ломающее изменение со своим
решением — в эту фичу его не подмешиваем.

## Полнота покрытия

Значения попадают в вывод только двумя путями: через
`objectToString`/`objectToJson` (все контейнеры и листья) и через `view`
в `Prop` (закрыт правилом выше). Санитайзер применяется в местах,
перечисленных в таблице, поэтому непокрытых путей не остаётся.

Дисциплина на будущее: **новый тип-контейнер обязан прогонять детей через
общие хелперы** `Loggable._sanitizeChild` + `Loggable._withSegment`.
Пропуск = дырка, поэтому хелперы одни на оба вывода и покрыты тестами.

То же касается **альтернативных рендереров уже существующего типа**.
`LoggableMultiData` рисуют четыре разных места: обходчик строки,
обходчик JSON, `LoggableMultiData.toString` и `LogMessage` в принтере
(ему нужна разбивка секций по строкам). Секционную раскладку они
дублируют по необходимости, но санитайз записи — нет: он живёт в
`Loggable.forEachMultiDataEntry`, и все четыре обязаны идти через него.
Рендерер, обошедший хелпер стороной, отдаёт значение секции обходчику
как **корень** — без имени, без сегмента пути, — и правила по `name`/
`path` на секции не срабатывают. Именно так и было до финального ревью:
принтер печатал секцию `password` при активном правиле-drop. Тест
`test/logger/sanitizer_e2e_test.dart` гоняет multi-data через настоящий
`ConsoleLogPrinter` именно поэтому.

`LoggableWrapper` прозрачен **во всех позициях**: и в корне (разворот в
`objectToString`/`objectToJson` до проверки корня), и у свойства, записи
`Map`, элемента коллекции — разворот в `_sanitizeChild`. Санитайзер
видит завёрнутое значение, а не обёртку, иначе `Loggable.from(password)`
прошёл бы мимо правил по содержимому. Если правило вернуло содержимое
без изменений, рендерится исходная обёртка — её `config` должен уцелеть;
замена рендерится напрямую, как и в правиле `view`.

## Циклы, лимиты, ленивость

Не трогаем: цикл по-прежнему рендерится как `↺ₙ` / `{":k": "cycle"}`
существующей защитой, лимиты коллекций (`collectionMaxCount`) работают
как раньше, ленивые и бесконечные `Iterable` не материализуются.

Для `collectionMaxCount` это верно буквально: обход останавливается до
того, как отсечённый элемент доходит до `obj2str`/`obj2json`, — правило
для него не вызывается.

Для бюджета длины (`collectionMaxStringLength`) — нет. Кандидат
рендерится (и тем самым санитизируется) ДО того, как известно, влезет
ли он в бюджет: размер узнаётся только по уже готовому тексту. Уже
отрендеренный и буферизованный элемент может быть задним числом
вытеснен многоточием, если не хватило места. Поэтому правило может быть
вызвано для значения, которое в итоге в вывод не попадёт.

Следствие для правил санитайзера: они обязаны быть свободны от побочных
эффектов (счётчики, аудит-лог, что угодно неидемпотентное) — сам факт
вызова не гарантирует, что значение будет напечатано. На корректность
вывода и отсутствие утечек это не влияет: значение, вытесненное
многоточием, в вывод не попадает независимо от того, что вернуло
правило.

## Ошибки

Исключение из санитайзера не перехватывается: оно выходит из
`objectToString`/`objectToJson` в вызывающий publisher. Для
`ConsoleLogPrinter` это исключение внутри `publish`, которое
`MultiPublisher` изолирует и отдаёт в `onError`; для `FileLogStorage` —
ошибка кодирования, которая уходит в его `onError` и заменяется
fallback-строкой без данных.

Это **слабее**, чем fail-closed у `Logger.transformer` (там лог просто не
публикуется). Документируем прямо: санитайзер обязан быть тотальным;
падение правила означает, что запись может быть выведена частично (в
`FileLogStorage` — служебной fallback-строкой, без пользовательских
данных).

## Издержки

- Санитайзер вызывается на каждое выводимое значение и на каждый вывод:
  лог, попавший и в консоль, и в файл, санитайзится дважды.
- Когда `Loggable.sanitizer == null` — одна проверка на `null` на
  значение, больше ничего.

## Что вне рамок

- `message`, `error`, `stackTrace`, теги, путь — правятся
  `Logger.transformer` + `Log.copyWith`.
- Санитайзация ключей `Map`.
- Разные правила для разных назначений (следствие глобального
  санитайзера).
- Готовые редакторы (`Redact.mask`, `Redact.last4`) — примитив +
  композиция, как в остальном пакете.

## Тестирование

- Ноль-оверхед: без санитайзера весь существующий вывод не меняется
  (проверяется существующим набором из 228 тестов).
- Контекст: `name`, `depth`, `path` для свойства, ключа `Map`, индекса
  коллекции, записи multi-data, корня; ленивость `path`.
- Замена: скаляра, контейнера (внутрь оригинала обход не идёт, дети
  замены — предлагаются), корня.
- `Sanitize.drop` в каждой позиции таблицы; разделители не ломаются
  (`{a: 1, c: 3}`, а не `{a: 1, , c: 3}`), в JSON ключа нет.
- Правило view: `prop(view:)`, `computed`, `fixed`/`round`,
  `LoggableView`, `LoggableMultiView` — в выводе нет оригинала.
- `LoggableWrapper` прозрачен; конвертеры типов; `Loggable`-объекты;
  builder'ы.
- Циклы и лимиты коллекций продолжают работать при активном санитайзере.
- e2e: секрет не доходит ни до `ConsoleLogPrinter`, ни до JSONL
  `FileLogStorage`; санитайзер действует и при прямом вызове
  `Loggable.objectToString(log.data)` (сценарий in-app просмотрщика).
